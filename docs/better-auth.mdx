# better-auth Integration

`@rafters/ledger/better-auth` wires audit logging and user soft delete into [better-auth](https://better-auth.com) 1.7 and later: `ledgerPlugin` for create, update, and delete audit hooks and, with `softDeleteUser: true`, soft delete of the user row. `createDeleteAuditCallback` is deprecated: the plugin audits hard deletes itself.

---

## Exports

```typescript
import { ledgerPlugin, createDeleteAuditCallback } from "@rafters/ledger/better-auth";
```

The peer range is `better-auth >=1.7.0 <2.0.0`. 1.7 added `databaseHooks.<model>.delete.before` and `delete.after`, which the soft delete and the delete audit are built on.

---

## `ledgerPlugin`

With `writeAuditEntry`, the plugin registers `databaseHooks` inside better-auth for the `create.after`, `update.after`, and `delete.after` lifecycle events on audited tables. Each event fires `writeAuditEntry` as fire-and-forget: errors are logged via `console.error` and never rethrow into the auth flow. Without it, and with `auditTables` set, the audit is [atomic](#atomic-audit).

```typescript
import { betterAuth } from "better-auth";
import { drizzle } from "drizzle-orm/d1";
import { uuidv7 } from "uuidv7";
import { ledgerPlugin } from "@rafters/ledger/better-auth";
import { auditLog } from "@rafters/ledger/drizzle/schema/sqlite";

export function buildAuth(env: Env) {
  const db = drizzle(env.DB);

  return betterAuth({
    database: drizzle(env.DB),
    plugins: [
      ledgerPlugin({
        // WARNING: account rows carry OAuth tokens and password hashes.
      // Redaction strips them, but audit account only with a real need.
      auditTables: ["user"],
        writeAuditEntry: async (entry) => {
          await db.insert(auditLog).values({
            id: uuidv7(),
            tableName: entry.tableName,
            recordId: entry.recordId,
            action: entry.action,
            oldData: entry.oldData ? JSON.stringify(entry.oldData) : null,
            newData: entry.newData ? JSON.stringify(entry.newData) : null,
            userId: entry.userId,
            ip: null,
            userAgent: null,
            endpoint: null,
            requestId: null,
            createdAt: new Date(),
          });
        },
      }),
    ],
  });
}
```

### Config

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `auditTables` | `readonly string[]` | `["user"]` | Any model in the better-auth schema, core or plugin: `user`, `account`, `session`, `verification`, `passkey`, `apikey`, `organization`, `member`, `invitation`, and so on. A name that is not a model throws at init. Session is excluded by default due to volume: once listed, every sign-in, refresh, sign-out, and revocation writes an entry. Verification is opt-in: its `value` column holds OTP codes and reset tokens, which redaction strips by table rule. Set it without `writeAuditEntry` for [atomic audit](#atomic-audit). |
| `writeAuditEntry` | `(entry: LedgerAuditEntry) => Promise<void>` | `undefined` | The callback path: called for each auditable event after the change, fire-and-forget. With `auditTables` set and no callback, audit is atomic instead. With neither, the default `["user"]` is hooked and nothing is written. |
| `softDeleteUser` | `boolean` | `false` | Soft-delete the user row instead of deleting it. See [Soft delete](#soft-delete-softdeleteuser). |
| `redactPatterns` | `readonly string[]` | `undefined` | Extra key patterns to redact. Redaction itself is always on. |

### Redaction (always on)

Every entry's `oldData`/`newData` pass through `redactTableRow` before your `writeAuditEntry` callback sees them. Redaction cannot be disabled, and it fails closed: an entry that cannot be redacted is never written. `Date` values pass through intact. Matching values are replaced with `"[REDACTED]"`.

**By key name.** The full default set (`DEFAULT_SECRET_PATTERNS`), matched case-insensitively as substrings of the key at any depth:

| Pattern | Catches, for example |
| --- | --- |
| `token` | `accessToken`, `refresh_token`, `idToken` |
| `secret` | `clientSecret` |
| `password` | `password`, `passwordHash` |
| `apikey` | `apiKey`, `ApiKey` |
| `api_key` | `api_key` |
| `otp` | `otp`, `otpCode` |
| `code` | `code`, `resetCode` -- and `postalCode`, `countryCode` |
| `hash` | `hash`, `backupHash` |
| `salt` | `salt`, `passwordSalt` |
| `jwt` | `jwt`, `sessionJWT` |
| `credential` | `credential`, `credentialId` |
| `privatekey` | `privateKey` |
| `private_key` | `private_key` |
| `authorization` | `Authorization` |
| `cookie` | `cookie`, `setCookie` |
| `key` | `key` (the apikey plugin's column), `keyId`, `publicKey` |

Substring matching over-redacts on purpose: `code` also strips `postalCode` and `countryCode`. Losing a harmless field from an audit payload is the safe direction. Add app-specific patterns via `redactPatterns`.

**By table.** Some columns hold secrets under a name that says nothing. `TABLE_SECRET_COLUMNS` redacts them by table, top-level key, exact name: `verification.value`, which holds OTP codes and reset tokens. Auditing `verification` is opt-in, and safe when you opt in.

**Not by value.** Redaction inspects key names only, never string contents. A JWT or hex token stored under an innocent key (`note`, `metadata.blob`) passes through. If your schema carries one, list that key in `redactPatterns`.

### Atomic audit

Set `auditTables` and leave out `writeAuditEntry`, and the change and its audit row are written in one database transaction: both exist or neither does. If the audit row cannot be written, the change does not happen and the caller gets the error.

```typescript
import { betterAuth } from "better-auth";
import { organization } from "better-auth/plugins";
import { ledgerPlugin } from "@rafters/ledger/better-auth";

export const auth = betterAuth({
  database: db, // a better-auth adapter with real transactions
  plugins: [
    organization(),
    ledgerPlugin({ auditTables: ["user", "account", "organization", "member"] }),
  ],
});
```

**How.** At init the plugin replaces better-auth's `context.adapter` with a wrapper, before `internalAdapter` is built from it. Every write to an audited model (`create`, `update`, `updateMany`, `delete`, `deleteMany`, `consumeOne`, `incrementOne`) runs inside one adapter transaction together with the audit insert. The wrapper sits under everything that writes, so plugin endpoints that call `ctx.context.adapter` directly are covered the same as `internalAdapter`. Inside a transaction better-auth already opened (sign-up with an OAuth account, for one), the audit row joins that transaction. The wrapper reads the row before an update or delete, so `oldData` is a true before-image, not the `{ changed }` of the callback path.

**The table.** The plugin declares a `ledgerAudit` model through its schema, so better-auth's migration tooling creates `ledger_audit_log` for you. With the Drizzle adapter, declare it in your schema under the key `ledgerAudit`. Every audited write adds one row:

| Column | Holds |
| --- | --- |
| `id` | UUIDv7 |
| `tableName`, `recordId` | The model and id of the row that changed |
| `action` | `INSERT`, `UPDATE`, `SOFT_DELETE`, or `DELETE` |
| `oldData`, `newData` | The row before and after as JSON text, redacted. `null` for the side that does not exist: `INSERT` has no `oldData`, `DELETE` and `SOFT_DELETE` no `newData` (a soft delete's `newData` is the row with `deletedAt` set) |
| `userId` | The actor, resolved as in [Attribution](#attribution); `null` when unknown |
| `subjectUserId` | The user the change concerns: the row's own id for `user`; the row's `userId` field for any other model that has one (`account`, `session`, `member`, `passkey`); `null` for a row with no `userId`, such as `organization` |
| `createdAt` | Write time |

`userId` and `subjectUserId` differ when one user changes another's data: an admin revoking a session has the admin as `userId` and the session's owner as `subjectUserId`. An event relay reads the change from `newData` (`oldData` for a delete) and the person it concerns from `subjectUserId`. A model whose owner is not in a `userId` field, such as an apikey owned through `referenceId`, has `subjectUserId` `null`; its data is still in the payloads.

**Actor.** For writes that pass through better-auth's `databaseHooks` (everything `internalAdapter` does), the actor is the hook context's session user, as in [Attribution](#attribution). A plugin endpoint that writes through `ctx.context.adapter` runs no hook, so its actor is the ledger context's `userId`: run requests inside `runWithLedgerContext`, or the entry's `userId` is `null`.

**What it needs.** Either an adapter whose `transaction()` is real (better-auth's built-in SQLite, Postgres, and MySQL through Kysely, and `drizzleAdapter` with `transaction: true` over a driver with transactions), or a Cloudflare D1 binding wrapped in `ledgerD1()`. `ledgerPlugin` throws at init on anything else.

### Atomic audit on Cloudflare D1

D1 has no interactive transactions. Its only atomic unit is `D1Database.batch()`, and better-auth's adapters expose no batch, so the transaction path above cannot run there. Wrap the binding you hand to better-auth:

```typescript
import { betterAuth } from "better-auth";
import { ledgerD1, ledgerPlugin } from "@rafters/ledger/better-auth";

export function createAuth(env: { DB: D1Database }) {
  return betterAuth({
    database: ledgerD1(env.DB),
    plugins: [ledgerPlugin({ auditTables: ["user", "account", "organization", "member"] })],
  });
}
```

**How.** For each write to an audited model the adapter wrapper runs better-auth's own write once in a capture scope. `ledgerD1` records the one SQL statement better-auth would have run instead of running it. Ledger then sends D1 a single `batch()`: the audit statements, the change, and the audit statements that read the changed row. The batch commits or rolls back as a whole, so a failed audit write undoes the change and a failed change leaves no audit row. Outside an audited write, `ledgerD1` is the binding unchanged. It needs `AsyncLocalStorage` (Workers: the `nodejs_compat` flag) to keep one request's writes apart from another's.

The audit row's JSON is built by SQLite inside the batch, from the table's own columns, so `oldData` is the row as it stood when the batch ran and `newData` is the row the batch left. Differences from the transaction path:

- The JSON holds the stored column values: a boolean is `0` or `1`, a date is its stored text.
- Secret columns are decided by the same redaction rules and written as the literal `"[REDACTED]"`; the column is never selected.
- Better-auth reads the rows an `update`, `updateMany`, `delete`, or `deleteMany` touches before the batch to know which audit rows to write. If the set of matching rows changes between that read and the batch, the batch fails a row-count check, rolls back, and the caller gets a `LedgerAtomicAuditError`; nothing was written and the write can be retried.
- `transaction()` on D1 cannot hold a transaction open. Calls inside it run in sequence, and each audited write is atomic with its own audit row, but two audited writes in one better-auth flow are two batches.
- better-auth must generate the row ids (its default). With `generateId: false` or `"serial"` the database assigns the id, the batch cannot name the new row, and the create throws.

**Not covered.** The audit table is not append-only (add the triggers from `sql/sqlite/audit.sql` for `ledger_audit_log` if you need that), `purgeUserData` does not read it, and failed sign-ins are not audit data. Do not list `ledgerAudit` in `auditTables`; init throws.

**Choosing a path.** `writeAuditEntry` keeps the callback path: the entry is written after the change, errors are logged and never thrown, and `auditTables` still names the tables. Use it where the adapter has no transactions and you do not wrap a D1 binding.

### `LedgerAuditEntry` shape

| Field | Type | Notes |
| --- | --- | --- |
| `tableName` | `string` | The table that changed (`"user"`, `"account"`, etc.) |
| `recordId` | `string` | Primary key of the affected row |
| `action` | `"INSERT" \| "UPDATE" \| "SOFT_DELETE" \| "DELETE"` | The operation |
| `oldData` | `Record<string, unknown> \| null` | Row state before the change; `null` for `INSERT`. On `DELETE`, the deleted row, redacted. |
| `newData` | `Record<string, unknown> \| null` | Row state after the change; `null` for `DELETE` or `SOFT_DELETE` |
| `userId` | `string \| null` | The acting principal. See [Attribution](#attribution). |

Note: better-auth's `update.after` hook does not expose the previous row state. `oldData` on an `UPDATE` entry is `{ changed }`, the change set `update.before` received in the same request, never a full before-image.

### Attribution

better-auth passes every `databaseHook` the endpoint context as its second argument. The plugin reads the actor from it, so attribution needs no middleware and does not depend on ledger's own context storage: better-auth's endpoint context carries it. `userId` resolves in this order:

1. The session user on the hook context (`ctx.context.session.user.id`).
2. The ledger context's `userId`, when the request runs inside `runWithLedgerContext`.
3. The target row's own id, for user sign-up (`INSERT` on `user`) and user deletion (`DELETE` or `SOFT_DELETE` on `user`) only. Anything else is `null`.

Which writes carry a session on better-auth 1.7: the session is set when an endpoint resolves it, through its session middleware or in its own body, so updates and deletes from an authenticated route carry it. That covers `updateUser`, the admin plugin's `updateUser`, `setRole`, and `banUser`, `unlinkAccount`, `revokeSession(s)`, `deleteUser`, and `verify-email` when the caller is signed in. A user created by sign-up does not: sign-up and sign-in never resolve the session, and the new session is created after the user, so the new user's own id stands in. A write through `internalAdapter` outside any endpoint gets no hook context at all.

`runWithLedgerContext` is still the way to attribute those session-less and out-of-endpoint writes, and to carry `ip`, `userAgent`, `endpoint`, and `requestId` for the rest of your audit trail. `assertLedgerContextAvailable()` remains an opt-in boot check for apps that rely on it.

### Delete entries

Every hard delete of a row in an audited table writes one `DELETE` entry from `delete.after`, with `oldData` set to the row better-auth read before deleting it and `newData` set to `null`. Covered: unlinking an account, revoking a session or signing out (with `session` listed), the user's sessions and accounts that `deleteUser` removes, and the user row itself when `softDeleteUser` is off. `delete.after` never fires for a delete a `delete.before` hook vetoed, so a soft-deleted user gets a `SOFT_DELETE` entry and no `DELETE`.

Bulk deletes (better-auth's `deleteManyWithHooks`, used by `deleteUser`, `revokeSessions`, and sign-out of every session) call the hook once per row, each with that row from a snapshot read before the delete. They never call it once with the where clause, so a bulk delete of three accounts writes three entries, each with its own `recordId`. Verification tokens consumed on use (`consumeOneWithHooks`) write one entry with the consumed row.

The actor resolves as in [Attribution](#attribution). For a `user` row with no session and no ledger context, it falls back to the deleted user's own id, the same as `SOFT_DELETE`.

## Soft delete (`softDeleteUser`)

With `softDeleteUser: true`, the plugin registers `databaseHooks.user.delete.before`. When better-auth is about to delete a user row, the hook:

1. Sets `deletedAt` (and `deletedBy`, when the user schema declares it) through better-auth's own adapter. No ORM handle is involved, so it works with any better-auth database adapter.
2. Writes a redacted `SOFT_DELETE` audit entry (if `writeAuditEntry` is set).
3. Returns `false`, which tells better-auth to skip the row delete.

Nothing throws. The `deleteUser` route goes on to revoke every session, clear the session cookie, and answer `{ success: true }`, so `authClient.deleteUser()` over HTTP sees a real success. Every path through better-auth's `internalAdapter.deleteUser` soft-deletes: self-service `deleteUser`, the email-token `/delete-user/callback`, and the admin plugin's `removeUser`.

The user schema must declare `deletedAt` (and optionally `deletedBy`) as better-auth fields, with `input: false` so clients cannot set them through `updateUser`. The plugin throws at init if `deletedAt` is missing.

```typescript
import { betterAuth } from "better-auth";
import { ledgerPlugin } from "@rafters/ledger/better-auth";

export const auth = betterAuth({
  database: drizzleAdapter(db, { provider: "sqlite" }),
  user: {
    additionalFields: {
      deletedAt: { type: "date", required: false, input: false },
      deletedBy: { type: "string", required: false, input: false },
    },
    deleteUser: { enabled: true },
  },
  plugins: [ledgerPlugin({ softDeleteUser: true, writeAuditEntry })],
});
```

`deletedBy` is the actor from the hook context's session user, else the ledger context's `userId`, so an admin's `removeUser` records the admin and a signed-in user deleting their own account records themselves. It is `null` only when neither names an actor. The `SOFT_DELETE` entry's `userId` resolves the same way and falls back to the deleted user's own id, as in [Attribution](#attribution).

### What better-auth still deletes

better-auth's `internalAdapter.deleteUser` deletes the user's session rows and **account rows** before it reaches the user row. The `delete.before` veto applies to the user row only, so:

- Sessions are revoked, which is what a deletion needs.
- Credential accounts (password hashes) and OAuth accounts (tokens, provider links) are **hard-deleted**. With `account` in `auditTables`, each one writes a redacted `DELETE` entry. Restoring a soft-deleted user means a password reset or a fresh OAuth link; the old credentials are gone.
- The user row, with its email, survives.

### Gate sign-in on `deletedAt`

better-auth's session resolution knows nothing about `deletedAt`. Because the row survives with its email, an OAuth sign-in with account linking can attach a new account to it and sign the "deleted" user back in. Gate session creation on `deletedAt`:

```typescript
import { APIError } from "better-auth/api";

databaseHooks: {
  session: {
    create: {
      before: async (session) => {
        const [u] = await db.select().from(users).where(eq(users.id, session.userId));
        if (u?.deletedAt) {
          throw new APIError("FORBIDDEN", { message: "Account deleted" });
        }
      },
    },
  },
},
```

### Hook order

better-auth runs plugin `databaseHooks` before the ones in your own config. Once the ledger hook returns `false`, better-auth stops: your own `databaseHooks.user.delete.before` does not run for that delete, and no `delete.after` hook fires. `user.deleteUser.beforeDelete` and `afterDelete` on the route still run, before and after the (skipped) row delete.

## `createDeleteAuditCallback` (deprecated)

Deprecated: `ledgerPlugin` with `user` in `auditTables` (the default) already writes a `DELETE` entry for a hard user delete from `databaseHooks.user.delete.after`. Using this callback alongside the plugin writes two `DELETE` entries for one delete. It stays only for setups that audit user deletes without the plugin, and will be removed in a future major.

For cases where you want hard delete (the user row is permanently removed) but still need an audit trail. This goes in `afterDelete`, not `beforeDelete`. It logs a `DELETE` entry and returns normally without throwing.

```typescript
import { createDeleteAuditCallback } from "@rafters/ledger/better-auth";

export const auth = betterAuth({
  user: {
    deleteUser: {
      enabled: true,
      afterDelete: createDeleteAuditCallback(async (entry) => {
        await db.insert(auditLog).values({
          id: uuidv7(),
          tableName: entry.tableName,
          recordId: entry.recordId,
          action: entry.action,
          oldData: entry.oldData ? JSON.stringify(entry.oldData) : null,
          newData: null,
          userId: entry.userId,
          ip: null,
          userAgent: null,
          endpoint: null,
          requestId: null,
          createdAt: new Date(),
        });
      }),
    },
  },
});
```

`afterDelete` receives no hook context, so the entry's `userId` is the ledger context's `userId` when the request runs inside `runWithLedgerContext`, and the deleted user's own id otherwise.

Errors inside `writeAuditEntry` are caught and logged; they do not propagate. The hard delete has already happened by the time `afterDelete` fires, so there is nothing left to abort.

Do not combine `createDeleteAuditCallback` with `softDeleteUser`. The route's `afterDelete` still runs after a soft delete, so the callback would record a `DELETE` that did not happen. Pick one.

## Full Setup

A complete `betterAuth` config with the plugin, user soft delete, the sign-in gate, and the user table wired correctly.

```typescript
import { betterAuth } from "better-auth";
import { drizzleAdapter } from "better-auth/adapters/drizzle";
import { drizzle } from "drizzle-orm/d1";
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";
import { eq } from "drizzle-orm";
import { APIError } from "better-auth/api";
import { uuidv7 } from "uuidv7";
import { ledgerPlugin } from "@rafters/ledger/better-auth";
import { softDeleteColumns } from "@rafters/ledger/drizzle/soft-delete/sqlite";
import { auditLog } from "@rafters/ledger/drizzle/schema/sqlite";

// Schema
export const users = sqliteTable("user", {
  id: text("id").primaryKey(),
  name: text("name").notNull(),
  email: text("email").notNull().unique(),
  emailVerified: integer("email_verified", { mode: "boolean" }).notNull().default(false),
  image: text("image"),
  createdAt: integer("created_at", { mode: "timestamp" }).notNull(),
  updatedAt: integer("updated_at", { mode: "timestamp" }).notNull(),
  ...softDeleteColumns,
});

// Auth factory
export function buildAuth(env: Env) {
  const db = drizzle(env.DB, { schema: { users, auditLog } });

  async function writeAuditEntry(entry: Parameters<typeof ledgerPlugin>[0]["writeAuditEntry"] extends (e: infer E) => unknown ? E : never) {
    await db.insert(auditLog).values({
      id: uuidv7(),
      tableName: entry.tableName,
      recordId: entry.recordId,
      action: entry.action,
      oldData: entry.oldData ? JSON.stringify(entry.oldData) : null,
      newData: entry.newData ? JSON.stringify(entry.newData) : null,
      userId: entry.userId,
      ip: null,
      userAgent: null,
      endpoint: null,
      requestId: null,
      createdAt: new Date(),
    });
  }

  return betterAuth({
    database: drizzleAdapter(db, { provider: "sqlite", schema: { user: users } }),
    user: {
      additionalFields: {
        deletedAt: { type: "date", required: false, input: false },
        deletedBy: { type: "string", required: false, input: false },
      },
      deleteUser: { enabled: true },
    },
    databaseHooks: {
      session: {
        create: {
          before: async (session) => {
            const [u] = await db.select().from(users).where(eq(users.id, session.userId));
            if (u?.deletedAt) {
              throw new APIError("FORBIDDEN", { message: "Account deleted" });
            }
          },
        },
      },
    },
    plugins: [
      ledgerPlugin({
        // WARNING: account rows carry OAuth tokens and password hashes.
        // Redaction strips them, but audit account only with a real need.
        auditTables: ["user"],
        softDeleteUser: true,
        writeAuditEntry,
      }),
    ],
  });
}
```

In this setup:

- User and account creates/updates write `INSERT` and `UPDATE` audit entries via `ledgerPlugin`.
- `deleteUser` sets `deleted_at` on the user row, writes a `SOFT_DELETE` audit entry, revokes the sessions, and answers success.
- The user row is preserved; its account rows are deleted by better-auth.
- A sign-in that reaches the soft-deleted row is rejected with 403.

## Relation to `createAuditedDb`

`ledgerPlugin` is better-auth-specific. They fire from better-auth lifecycle hooks, not from Drizzle operations.

`createAuditedDb` (from `@rafters/ledger/drizzle`) intercepts `db.delete()` calls on your Drizzle instance and converts them to soft-delete updates automatically. These two systems are independent. `createAuditedDb` does not affect better-auth's internal delete operations, and `softDeleteUser` does not affect your application's direct Drizzle calls.

Use both if you want full coverage: `createAuditedDb` handles application-layer deletes on any table; `softDeleteUser` handles better-auth's own user deletes.
